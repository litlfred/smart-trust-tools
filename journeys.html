User journey coverage (DRAFT journeys J1 to J4)

What the HCERT library must do for each step of the workshop storyline, and whether it does. OHS Player, OHS Stack and the CHW and wallet apps are consumers of the Kotlin library; rendering, scanning, storage, HTTP and FHIR record keeping are theirs. Source: stakeholder directive dir-journeys, 2026-10-20.

VHL: what the specifications say, and where they disagree

Changes raised upstream: WorldHealthOrganization/smart-trust#130 (subclaim 5 is a VHL, a CBOR map), WorldHealthOrganization/smart-trust-phw#17 (payload types match SMART Health Links), and a patch for IHE ITI.VHL in upstream/ihe-iti-vhl/ (ITI-YY3 key 5 as a CBOR map, example fixes). Open issues OI-21 to OI-29.

The IHE ITI VHL profile and the WHO VerifiableHealthLinkPayload model share the SMART Health Links payload fields, but:

  • IHE’s manifest is a FHIR List search returning a searchset Bundle of DocumentReferences (ITI-YY5), not the SMART Health Links files[] manifest; the Bundle is not signed, and the journey’s “signed VHL manifests” exist in neither specification.
  • The value at hcert key 5 is a vhlink:/ text string in ITI-YY3 but a decoded JSON object in the ITI-YY4 example; HCERT 3.2.7.1.5 calls it a SMART Health Link (OI-06).
  • WHO requires type (vhl) and types exp and v as strings; IHE has no type and uses numbers.
  • JWE alg/enc are not normative (the example is dir / A256GCM); no zip.
  • Requester authentication (RFC 9421 HTTP signatures, UDAP, or a VC) and the DID trust list’s mapping to a COSE kid are under-specified.
