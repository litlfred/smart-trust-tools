HCERT and VHL library (Kotlin Multiplatform)

The Kotlin implementation of the HCERT pipeline and Verifiable Health Links, for the JVM (Android as-is) and Node: hcert-api, the declarations wit2kotlin generates from the WIT contract, and hcert-core, the behaviour (deterministic CBOR, COSE_Sign1 ES256/PS256, ZLIB, Base45, HC1, the trust list, verification, the VHL payload, the ITI-YY5 manifest request and JWE dir/A256GCM). No third-party runtime dependency; every build artefact is pinned in gradle/verification-metadata.xml.

A skill states the capability; this Tool is one way to exercise it. Each skill’s declared input and output contract follows, where it has one.

Step 1: choose the logical model and hcert subclaim for a use case, from the registry the IG defines.

hcert-assemble-payload

Step 2: build and validate the payload against its logical model (DVCMin, or a VHL payload), keeping unknown elements.

Source: skills/hcert/hcert-assemble-payload.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-assemble-payload/{input,output}.schema.json).

hcert-build-cwt

Step 3: wrap the payload in a CWT claim set (iss, iat, exp, hcert -260) inside the DSC’s validity.

Source: skills/hcert/hcert-build-cwt.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-build-cwt/{input,output}.schema.json).

hcert-encode-cbor

Step 4: serialise as RFC 8949 deterministic CBOR, and decode untrusted CBOR within limits.

Source: skills/hcert/hcert-encode-cbor.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-encode-cbor/{input,output}.schema.json).

hcert-sign-cose

Step 5: sign as COSE_Sign1 (ES256 or PS256) in two phases, the private key staying with its holder.

The skill declares no I/O contract (schemas/skills/hcert-sign-cose/{input,output}.schema.json).

hcert-compress

Step 6: ZLIB/DEFLATE after signing, and bounded inflation.

Source: skills/hcert/hcert-compress.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-compress/{input,output}.schema.json).

hcert-encode-base45

Step 7: RFC 9285 Base45, decoded strictly.

Also satisfied by: hcert-rust.

hcert-prefix-context

Steps 8 and 9: the HC1: context identifier, giving a QR-ready string the application renders with its own QR encoder.

hcert-verify

Verify an HC1 string or raw COSE: the steps upwards, trust lookup by kid, signature, key usage, time and payload; or read it explicitly unverified for triage.

Source: skills/hcert/hcert-verify.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-verify/{input,output}.schema.json).

hcert-trust-list

Hold the trusted DSCs the host obtained (PEM, DER, GDHCN DID trustlist v2) and find every candidate for a kid.

Source: skills/hcert/hcert-trust-list.md.

Also satisfied by: hcert-rust.

The skill declares no I/O contract (schemas/skills/hcert-trust-list/{input,output}.schema.json).

vhl-share

Issue a VHL: a key, documents encrypted as JWE dir / A256GCM, and the payload as a CBOR map at HCERT key 5 (journey J4.0). A plain SMART Health Link is issued by the same steps with its own carrier.

Source: skills/vhl/vhl-share.md.

The skill declares no I/O contract (schemas/skills/vhl-share/{input,output}.schema.json).

vhl-receive

Use a VHL: verify it, build the ITI-YY5 manifest request with its HTTP Message Signature, read the manifest Bundle and decrypt each document (journey J4.1). A plain SMART Health Link is received by the same steps, without the HCERT verification.

Source: skills/vhl/vhl-receive.md.

The skill declares no I/O contract (schemas/skills/vhl-receive/{input,output}.schema.json).

hcert-library-architecture

The rules every implementation follows: Kotlin first, Rust second, one contract, a synchronous core with no I/O, open standards, no payload in logs.

Source: skills/hcert-library/hcert-library-architecture.md.

Also satisfied by: release-packaging.

The skill declares no I/O contract (schemas/skills/hcert-library-architecture/{input,output}.schema.json).

How it is deployed and reached

  • Command line. From the repository root: gradle -p tools/hcert-kotlin --dependency-verification strict build.
  • GitHub Actions. No workflow in this checkout runs its command.

As an API: its operation in the OpenAPI document and the MCP tool list of its layer.

   
install none
runtime gradle, java
network yes

When a host it reaches is refused:

host / error remedy
repo.maven.apache.org none: Re-run through Google’s mirror of Maven Central: --init-script gradle/central-mirror.init.gradle. The verification metadata still pins every artefact’s sha256, so the mirror is trusted for nothing.
plugins.gradle.org none: The Kotlin plugins are also on Maven Central; the same mirror init script serves them.
when to choose it  
when An application on the JVM, Android or Node issues, verifies or reads an HCERT, or shares or receives a VHL; or a change to the contract or the core is built and tested.
limits No QR rendering (the host renders the HC1 string), no HTTP (the host sends the ITI-YY5 request it builds), no key storage (the host signs the bytes prepare-sign returns). Rust (native and WebAssembly) is the second implementation, in tools/hcert-rust.
cost About a minute cold for the JVM and JS tests; Gradle downloads only artefacts the verification metadata lists.
