The library SHALL implement issuance (steps 1 to 9) and verification (QR Code Generation section 11) of HCERT QR codes.

Every data type in the API contract, wire schema and payload models SHALL trace to an openly available standard: IETF CBOR/CDDL (RFC 8949, RFC 8610) for the wire format, HL7 FHIR data types and W3C XSD datatypes for payload elements, W3C JSON-LD and SHACL for payload semantics, ITU-T X.680 for certificates, and I-JSON (RFC 7493) for JSON files. Paywalled standards SHALL NOT be used as type or schema references.

OI-01 Reference script output is not reproducible byte for byte (fix upstream)

QR Code Generation 12 and 13 say the script "regenerates the example above byte for byte". It does not. The DSC is signed by the SCA, and the COSE_Sign1 by the DSC, using randomized ECDSA, so every run produces a different DSC, a different kid and different HC1 strings. Running the script at PR head 50bcb25 twice produced kids ZfzK2Csfpsk= and 2sMkNOHFctA=, against WHM+BYqqZiE= in the PR, and different HC1 strings on every run. The committed artefacts are internally consistent: both committed HC1 strings verify against the committed DSC and the kid matches. The sizes in 12.5 are not stable either: the deflated size came out as 283 bytes instead of 282, and the HC1 length as 429 characters instead of 427.

Suggested resolution: Either use RFC 6979 deterministic ECDSA for both signatures, or reword the claim to "regenerates an equivalent example" and treat the committed JSON and PEM as the normative test vector. The library requirements assume the committed artefacts are the vector (STT-TST-001).

OI-15 Asynchronous crypto and I/O across the WIT boundary

WASI 0.2 component calls are synchronous. WebCrypto (the natural crypto backend for Kotlin/JS on Node and browsers) is promise-based, as are remote KMS signers and HTTP fetches. The design avoids async callbacks into the host: signing is two-phase and trust lists are loaded by the host. The Rust component verifies with in-WASM RustCrypto, so verify stays synchronous. Kotlin/JS must either use Node's synchronous crypto module (Node only) or expose a Promise-returning verify, which would diverge from the jco surface. Decide before implementation; revisit when WASI 0.3 async is stable.

Sources: WIT, WebAssembly Component Model IDL; W3C Web Cryptography API

Affects: STT-GEN-012, STT-ISS-004

OI-16 WIT type-system limits

WIT has no recursive types, so generic CBOR crosses as encoded bytes and only DVCMin and VHL are typed records. s64 becomes bigint in JavaScript, so it is used only for NumericDate, and subclaim numbers are s32. result is thrown as ComponentError by jco, so APIs whose failures are expected (verify) return a variant instead.

Sources: WIT, WebAssembly Component Model IDL

Affects: STT-GEN-010

The HCert logical model puts DVCMin at subclaim -6, and the PR 129 example issues a DVCMin with ICD-11 codes. So no concrete model exists for a non-PreQual DVC: either DVCMin should not be abstract, or a concrete ICD-11 profile is needed.

DVCMin.s is bound (extensible) to $GENDER, which smart-trust-phw aliases to http://hl7.org/fhir/administrative-gender, the CodeSystem URL. A binding must reference a ValueSet: http://hl7.org/fhir/ValueSet/administrative-gender.

Affects: STT-PAY-010

OI-19 Upstream home for the CDDL and JSON-LD artefacts (fix upstream)

OI-20 CDDL validator deviations (cddl-rs / pycddl)

The only Python CDDL validator, pycddl (wrapping the Rust cddl crate), deviates from RFC 8610 in four ways found here: .cbor inside arrays is applied to the wrong items; .regexp is not implicitly anchored; escaped regex classes such as \s are treated as literals; and map closure is not enforced across group-choice alternatives. The CDDL files stay spec-correct, and tools/check_models.py works around the first three. The schema avoids relying on the fourth. Cross-check with a second validator (e.g. cddlc) before upstreaming.

Sources: RFC 8610 Concise Data Definition Language (CDDL); RFC 9682 Updates to the CDDL grammar

Affects: STT-CBR-004
